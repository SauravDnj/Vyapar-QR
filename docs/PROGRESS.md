**Known environment constraints** (apply to every relevant row below):
- **Database engine: MySQL, not Postgres.** Switched at the user's direction from the original PLAN.md spec (PostgreSQL) to a local MySQL 9.7 server already installed on this machine (`root` / see local `.env`, not committed). Prisma schema, adapter (`@prisma/adapter-mariadb`), and all connection config target MySQL. `docker-compose.yml` mirrors this with a `mysql:8.4` service for production parity.
- No Docker in this sandbox → `docker-compose.yml`/Dockerfiles are written but not run here. Locally, this machine's native MySQL 9.7 server and a portable Redis (`.tools/redis/redis-server.exe`, gitignored) stand in so the backend can actually be tested.
- Razorpay, Google Sheets API, SMTP: no credentials available → those integrations are code-complete against test-mode/mocked config but not live-tested.
- No Android device → payment deep-link buttons (`tez://`, `phonepe://`, `paytmmp://`) are code-complete but not device-verified.
- No VPS/domain → production deploy tasks (P1-51–P1-53) are code-complete but not actually deployed.
- No MinIO/S3 in this sandbox → file uploads (logo, payment QR images, generated QR codes) use a local-disk `StorageService` (`apps/api/src/storage`) behind the same `save(buffer, ext) -> url` shape an S3 implementation would have, served back via `/uploads/*`. Swapping in real S3/MinIO later only touches that one file.
- Dev server ports are pinned (`apps/admin` → 3001, `apps/landing` → 3002) to match `CORS_ORIGINS`/`ADMIN_APP_URL`/`LANDING_APP_URL` in `apps/api/.env` — Next's unpinned default of 3000 previously caused a silent CORS failure ("Failed to fetch") on every admin API call. Always start them via `pnpm --filter admin dev` / `pnpm --filter landing dev` from the repo root (not `cd apps/admin && pnpm dev` — a stray `apps/admin/pnpm-workspace.yaml` with just `allowBuilds` overrides makes pnpm treat that directory as its own workspace root when invoked from inside it, hiding `@qrhub/config` etc.).
- **A long-running `next dev` process goes stale after a `pnpm install` changes `node_modules` underneath it** — every page (not just newly-added ones) started 500ing with `Module not found: Can't resolve '../../../build/output/log'` deep inside Next's own compiled `resolve-opengraph.js`, on both `apps/admin` and `apps/landing`, after this session's several `pnpm install` runs. Not a code bug — killing the stale process and re-running `pnpm --filter admin dev` / `pnpm --filter landing dev` fixed it immediately (`✓ Ready in ~3-5s`, all routes back to 200). If dev servers were already running before you run `pnpm install` for any reason, restart them afterward before trusting a 500.
- **Something in this environment (observed across two separate sessions now) silently rewrites root/app `package.json` and `pnpm-workspace.yaml` files** — this session watched `pnpm install` bump `typescript` to an unreleased-support `7.0.2` (breaking `typescript-eslint`) and briefly strip `apps/admin`'s `@qrhub/*` workspace dependencies entirely, both self-correcting on a later `pnpm install` but landing on the wrong `typescript` version. If `pnpm lint`/`typecheck` suddenly break workspace-wide with no corresponding code change, check `git diff`-equivalent (a manual re-read against this doc's known-good versions) on `package.json`/`pnpm-workspace.yaml` before assuming the code is at fault — `typescript` should stay on the `^5.7.x` line everywhere except `apps/api` (`^5.7.3`), and `pnpm-workspace.yaml` must keep `packages: ["apps/*", "packages/*"]` plus `allowBuilds: {'@prisma/engines': true, bcrypt: true, prisma: true, sharp: false, msgpackr-extract: false, unrs-resolver: false}`.
- **`pnpm --filter api dev` (`nest start --watch`) crashes on boot under the machine's current Node version (v25.9.0) with `ERR_MODULE_NOT_FOUND: Cannot find module '...\packages\types\src\theme'`** — reproduced twice in a row, always right after a clean `Found 0 errors` compile. Root cause: `packages/types` ships no build step (`package.json`'s `main`/`types` point straight at `./src/index.ts`) and its barrel file re-exports without file extensions (`export * from './theme'`) — that's fine under a bundler/`ts-node`-style loader, but this Node version's native TypeScript execution enforces Node's stricter ESM resolution (explicit extensions required on relative specifiers), so it throws instead of falling back to extension-guessing. Not caused by this session's changes — the same extensionless pattern already existed on the other 3 barrel-file lines (`./plan`, `./rendering`) before this session added a 4th (`./staff`) the same way, and it would fail identically without that addition. Given the machine also had ~34 concurrent `node.exe` processes at the time (heavy concurrent multi-session load), this could not be reliably root-caused further or fixed without risking a conflicting edit to a shared, actively-edited file (`packages/types`) — flagging here rather than guessing at a fix. Likely remedies for a future pass: add explicit `.ts`/`.js` extensions to `packages/types/src/index.ts`'s re-exports, or give `packages/types` a real build step, or pin `apps/api`'s dev script to a Node version with looser ESM resolution.

## Phase 12 — WhatsApp CRM + AI Chatbot

Built at the user's direct request: connect WhatsApp into the CRM for easy customer messaging, send Google review requests over WhatsApp, and add an AI chatbot with automation on the same number. Builds directly on top of the `WhatsappService`/`whatsapp-config.provider.ts` foundation from Phase 11 (same shared Meta Cloud API number) rather than duplicating it — extended it with conversation storage, an AI reply engine, and both a client-facing CRM UI and a public inbound webhook.

**Architecture decision (asked, not assumed):** every client shares the **same one platform-wide WhatsApp Business number**, rather than each client connecting their own — this was an explicit choice offered to and confirmed by the user, matching how Razorpay/SMTP/Sheets are already "configure once at the platform level," and avoiding requiring every client to set up their own Meta Business account. The practical consequence: an **inbound** message can't carry a "which business is this for" signal on its own, so it's routed to whichever client this phone number most recently exchanged a message with (`WhatsappService.handleInbound`) — a phone with no prior history on the number is logged (`WhatsappMessage.clientId: null`) but can't be routed or auto-replied to. This is a real, inherent boundary of the shared-number model, not a bug, and is called out directly in code comments.
